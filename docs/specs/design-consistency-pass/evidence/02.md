### Slice 3: Master Key sources, first-run generation and CLI

Tests: `tests/service/test_keys.py` (9 cases) and `tests/cli/test_credentials.py` (5 cases).
Happy paths cover environment and a real Docker-secret-style file, generation and committed
Secret/Provider saves through the CLI. Boundary/failure cases cover missing/empty/malformed
keys, wrong decoded length, conflicting sources, unreadable/non-ASCII files, wrong Master
Keys and generation after data exists or a key is configured. Key files remain unchanged.
The generation command prints exactly one key line without storing a Data Key or modifying
the environment; subsequent saves require the Reader to supply the generated key.
Prompts hide credential input, and actual CLI log files and terminal output exclude the
sentinel on both success and failure. Database bytes exclude the sentinel too. Failed saves
leave existing credentials unchanged. No external Provider network boundary is introduced.

Red: `uv run pytest tests/service/test_keys.py tests/cli/test_credentials.py -q --tb=short`
— 14 failed. Excerpts: `read_master_key -> NotImplementedError`, `No such command 'secret'`,
`No such command 'key'`. These show missing source resolution and CLI behavior.
Green: same command — 14 passed. Commit: `de7a685` (tests committed with implementation).

## Implementation choices

- AES-256-GCM using cryptography, random 12-byte nonces generated at the storage edge;
  authenticated context binds Data Keys to Readers, and credentials to Reader/type/record id.
- No new metrics: ticket specifies none, and credential operations do not need metric labels.
- Provider credentials have no public decryption command; Gateway use belongs to ticket 09.
- No external ticket exists (`external: null`); no tracker writes.
- Key setup is explicit (`news key generate`) after migration and before credential saves.
  The generated key is printed once per explicit setup invocation, never retained by the app.
  Re-running that command before any key/data exists is allowed; once configured or used,
  generation is refused. This follows ADR 0009's optional first-local-run generation.
- Repo-specific encryption rules and the versioned primary source are in `docs/standards.md`;
  usage and key-failure behavior are documented in `docs/credentials.md`.

## Deployment verification checklist

- Initialize a Master Key once; save it outside the database and supply it through
  `NEWS_MASTER_KEY` or `NEWS_MASTER_KEY_FILE` for subsequent invocations.
- Save a test Secret and Provider, restart with the same key, and confirm the Secret is
  usable by the service. Inspect credential rows: only ciphertext, no plaintext credentials.
- Supply a different Master Key and confirm credential use fails without replacing data.
- Check the CLI JSON log and server stdout: no test credential or Master Key value appears.
