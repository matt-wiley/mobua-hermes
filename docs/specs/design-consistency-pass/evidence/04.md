## AC-49: exact dependency pins

Tests: `tests/service/test_implementation.py` (25 cases), pure, no mocks.

- Happy path: `feedparser==6.0.11` accepted; `===`, extras and environment markers accepted.
- Failure modes: `feedparser>=6` rejected naming `code[main.py].dependencies.1`; bare names, `~=`,
  `==6.*`, ranges, multiple specifiers and direct URLs rejected. Malformed metadata (invalid TOML,
  two `script` blocks, non-list, non-string entries, invalid PEP 508 strings) is rejected rather
  than skipped.
- Boundaries: empty source, no block, `dependencies = []`, block without `dependencies` all accepted.
  CRLF line endings cannot hide a block from the check. Only `.py` files are read; every one is checked.
- Combined validation: `validate_implementation` reports Manifest errors (prefixed `manifest`) and
  pin errors together and returns the parsed Manifest when valid. It lives in
  `news.service.implementation` so Test Runs (15) and Plugin Runs (05/06) reuse it rather than
  re-parsing; those tickets must call it.
- Edge cases: arbitrary equality (`===`) counts as an exact pin; `==6.*` does not.

`packaging` (already installed transitively at 26.3) is now a declared dependency for PEP 508 parsing.

Red: `uv run pytest tests/service/test_implementation.py -q --tb=line`: 25 failed at scaffolded
`NotImplementedError` stubs. After implementing, two failures were test defects, not missing
behavior. The helper emitted double-quoted TOML that a `"3.11"` marker broke. And adjacent blocks

## AC-68: permanent, immutable Plugin Revisions

Tests: `tests/service/test_immutability.py` (+7 cases, 1 renamed).

- `session.delete()` of a committed Plugin Revision raises `ImmutableRevisionError` (operation
  `delete`, message "permanent") at flush; the stored row is unchanged after rollback.
- ORM-enabled bulk `delete(PluginRevision)` and bulk `update()` of Plugin Revisions, Channel
  Revisions and Bindings are refused by a `do_orm_execute` guard, and stored rows are unchanged.
  These statements previously bypassed the flush guard entirely.
- A Plugin Revision still pending insert can be discarded (expunged); Channel Revision and Binding
  deletes stay unblocked (renamed test). The ticket says not to invent Channel or Binding deletion
  policy.
- Draft rows stay mutable and deletable: `save_draft` uses a bulk ORM `update(PluginDraft)` and all
  Draft save/delete tests still pass. Promotion's own Draft delete is a bulk ORM delete.
- No archive/delete surface: `test_no_endpoint_archives_or_deletes_revisions` (API route inventory)
  and `test_cli_has_no_revision_archive_or_delete_command`.
- Migrations use Alembic `op` and are the explicit schema-transition boundary; they do not pass
  through the ORM guard.

Red: the first run failed for an incidental reason: foreign keys blocked the writes against bound
or current Revisions (`IntegrityError: FOREIGN KEY constraint failed`). The tests were rewritten to
target an unreferenced, non-current Revision with writes the database would otherwise accept.
Second red: 5 failed with `Failed: DID NOT RAISE ImmutableRevisionError`. Green: 19 passed.

## AC-65: atomic promotion

Tests: `tests/service/test_promotion.py`, `tests/api/test_revisions.py`, `tests/cli/test_revisions.py`.

- Happy path: new Revision is Reader-created, numbered next, records the Draft's parent, copies
  Manifest/code exactly, becomes current; only that Draft is deleted; sibling Drafts and Bindings
  are unchanged. The service flushes and does not commit.
- Failure modes. Each is checked in the same Session before rollback, then committed state is
  checked on a fresh Session.
  - Invalid TOML, unpinned dependencies, and both together: field errors.
  - A stale or future expected version: conflict.
  - Unknown or foreign Drafts: not found.
  - A failed commit, using the real SQLite deferred-constraint failure from `tests/db_failures.py`
    on the Draft DELETE: rolled back.
- Races: the conditional writes catch a competing writer. A `before_cursor_execute` hook commits on
  a second real connection just before the Revision INSERT. Two cases:
  - A racing current-pointer change gives `CurrentSelectionConflict`.
  - A racing Draft save gives `DraftConflict`.

  After the caller's rollback the committed state shows no new Revision, the Draft intact and the
  other writer's change preserved. Writes made before a race conflict are left to the caller's
  rollback, which every surface does (documented in `drafts.py`).
- Ordering: version is checked before validation (stale invalid Draft gives a conflict).
- Surfaces: API 201/422/409/404/503 and CLI exit 0/1 with nothing on stdout after failures. Commit
  failures on Draft DELETE, Revision INSERT and pointer UPDATE report no success and leave state
  unchanged.

## AC-66: siblings, older parents, numbering

- Two sibling Drafts promote to Revisions 2 and 3, both with the starter as parent; a third sibling
  remains editable (`save_draft` advances it to version 2).
- An older-parent promotion without confirmation is a `confirmation_required` conflict with no
  changes. With confirmation it promotes and copies the Draft as-is: the code is the Draft's, not
  merged with the current.
- A changed current selection after confirmation gives `stale_current_selection`.
- After selecting the starter as current, the next promotion is numbered 4 (from the whole history),
  not 2.
- Pure rule `selection_problem`: 7 parametrized cases, including no current pointer.
- API and CLI repeat the confirmation flow (`--confirm-current`, `expected_current_revision_id`).

## AC-67 / AC-69: history and current selection through shared services

Tests: `tests/service/test_revision_history.py` (18), `tests/api/test_revisions.py`,
`tests/cli/test_revisions.py`.

- History lists every Revision in number order with parents, Manifest, code, creator and UTC
  `created_at`, plus the current selection.
- Selecting an older Revision changes only the pointer; no Revision is created and Bindings stay
  where they are. Re-selecting the current Revision is allowed.
- Selection always needs the expected current Revision. A stale one is a logged conflict with no
  change.
- Rejected without changes:
  - unknown, other-Plugin, foreign and Built-in Revisions: `revision_id` field error;
  - foreign, Built-in and unknown Plugins: not found, with identical API bodies for foreign and
    unknown.
- Agreement between surfaces:
  - CLI `plugin revision list` output equals the API `GET .../revisions` body.
  - API `PUT .../current-revision` returns the same body as a following `GET`.
- Output is printed or returned only after commit; commit-failure tests show no success output.
- Request shapes: zero/boolean versions, malformed UUIDs, extra fields and missing confirmation
  give 422. The CLI requires exactly one of `--directory`/`--expected-version` (usage error, exit 2).
- AC-63 (promote half): CLI promote with `--directory` uses only the version marker; unsaved local
  edits are not promoted (`test_cli_promotes_saved_contents_not_unsaved_local_edits`). A stale
  workspace promotion is a conflict. `read_marker_version` has 4 unit tests in
  `tests/service/test_workspaces.py`.
- Promotion does not require a retained successful Test Run (no such record exists).

A real defect was found at the API seam. A just-created Revision's `created_at` was timezone-aware,
but SQLite returns stored times without a zone, so promote and history serialized the same Revision
differently. `RevisionDetails` now normalizes stored times to UTC. Covered by the API equality
assertion and a service assertion.

Red: services 35 failed at scaffolded `NotImplementedError` stubs. API: 19 failed (`{"detail":"Not
Found"}`, no routes). Three foreign-target cases passed trivially because a missing route also
returns 404; they now exercise real behavior. CLI: 16 failed ("No such command"). Workspace marker:
4 failed at a stub. Green: services 35, API 22, CLI 16, workspaces 49 passed.

The pre-existing route inventory test (`tests/api/test_app.py`) was updated on purpose to include

## AC-81: lifecycle events on both surfaces

- Service tests assert exact event dictionaries:
  - `plugin_draft.promoted`: Reader, Plugin, Draft, parent and new Revision ids.
  - `plugin_draft.rejected`: reason `invalid_implementation` and field codes only.
  - `plugin_draft.conflict`: operation `promote`/`select_current`, expected/actual versions or
    current-selection ids, and reason.
  - Selection conflicts have no Draft id.
- `test_api_logs_lifecycle_events_to_stdout_with_ids_and_no_source` runs one API flow and parses
  server stdout. Events, in order:
  1. save conflict (from 03)
  2. promotion rejection
  3. stale promotion conflict
  4. promotion
  5. confirmation conflict
  6. selection conflict
  7. Draft deletion (from 03)

  All are `info`, with Reader/Plugin ids on every line.
- `test_cli_logs_lifecycle_events_to_its_log_file_without_source` runs the same 04 events plus
  deletion through the CLI and parses the configured log file. CLI stdout carries no log lines. The
  03 CLI save conflict is covered by `test_cli_stale_workspace_fails_without_changing_database_or_marker`.
- Payload exclusion: saved code carries a credential-shaped sentinel (`SENSITIVE_sk-live-sentinel`)
  and an unpinned requirement. Neither the sentinel nor the requirement text (`feedparser`) appears
  in logs. Field errors with the requirement text go only to the invoking caller (HTTP body or CLI
  stderr). No metrics were added (ticket: "No new metrics").
