| 3 | AC-53 Channel-id check: how Channel-owned tables are identified (FK heuristic skips `channel_revision` and indirect ownership) | resolved | Each model declares its scope in `Table.info` (`{"scope": "app" \| "reader" \| "channel"}`). The schema test asserts: every migrated table is classified (`alembic_version` is the one known app-wide non-model table); `reader` tables have a Reader id (branch 2), `channel` tables also have `channel_id`; and any table with an FK to a Channel-owned table is itself declared `channel`. `plugin`/`plugin_revision` are `reader`, with nullable `reader_id` for Built-ins. `READER_SCOPE_EXEMPT_TABLES` is removed. As in branch 2, the `channel` table's own `id` is its Channel id. |
| 4 | Revision immutability (D-2): enforce or keep by convention | resolved | A service-layer ORM `before_flush` guard raises if a Plugin Revision, Channel Revision or Plugin Binding has modified attributes. Updates only: deletes are a non-goal until Channel or Plugin deletion is specified. Drafts (plugin-drafts grill) are not guarded. Rejected: DB triggers (non-portable, ADR 0013); convention only (unenforced). |
| 5 | Migrations packaging: `alembic/` outside the package breaks `news db upgrade` from a wheel | resolved | Move to `src/news/migrations/` with `script_location = news:migrations`. `migrate()` builds its Alembic config in code (no `alembic.ini` lookup, no `parents[3]`). Rejected: source-tree-only plus an ADR (ties deployment to the repo layout). |
| 6 | CLI log stream: JSON logs and CLI output share stdout | resolved | Direction decided by the user: the CLI sends service-layer logs to a file; the API/server keeps JSON on stdout as today, so CLI stdout carries only command output. Rejected: CLI logs to stderr; everything on stdout as JSON; the CLI hiding logs below warning. 6a, location (resolved): default `$XDG_STATE_HOME/news/cli.log`, falling back to `~/.local/state/news/cli.log`, directory created if missing, no new dependency; overridable with `--log-file` / `NEWS_CLI_LOG_FILE`; the container image is expected to set `NEWS_CLI_LOG_FILE=/data/logs/cli.log` (wired by the container ticket). Rejected: the current directory; beside the SQLite file. 6b, format and growth (resolved): JSON lines using the same structlog processors and renderer as the server; append-only with no in-app rotation (non-goal: CLI volume is tiny, and `RotatingFileHandler` is unsafe across concurrent CLI processes; hosts may use logrotate `copytruncate`). Rejected: a human-readable file format; size-based rotation now. 6c, unopenable log file (resolved): fail fast before any work, with exit 1 and a stderr message naming the path, the OS error, and the override (`--log-file` / `NEWS_CLI_LOG_FILE`). Rejected: warn and fall back to stderr (close to a silent fallback, since scripts often discard stderr). 6d, pointing to the log (resolved): expected failures print their specific message on stderr plus `Logged to <path>.`; unexpected exceptions are caught by a top-level CLI handler that logs `error cli.unexpected_error` (command, `exc_info`) to the file, prints `Unexpected error: <Type>: <message>. Details logged to <path>.` on stderr, and exits 1. Rejected: tracebacks on the terminal; no pointer. 6e, standards wording (follows from the above): the repo override in `docs/standards.md` becomes "Logging: structlog, as JSON lines. The server process writes to stdout; the CLI writes to a log file (`--log-file` / `NEWS_CLI_LOG_FILE`, default under `$XDG_STATE_HOME/news/`), so its stdout carries only command output." |
