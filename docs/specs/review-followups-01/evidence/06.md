# Evidence: review-followups-01-06

What changed:
- `news.service.models` gains `IMMUTABLE_MODELS` (`PluginRevision`, `ChannelRevision`, `PluginBinding`), `ImmutableRevisionError(table, attributes)`, and a `before_flush` listener, `_reject_revision_updates`.
- The listener is registered on the `Session` class itself, not on one sessionmaker. Every session in a process that has imported the models is guarded: the CLI's `_transaction`, the future API, and the tests' plain `Session(engine)`. It sits in `models.py` because any code that can flush these rows has already imported that module.
- For each dirty instance of a guarded class, the listener collects every mapped attribute, columns and relationships alike, whose history has changes. If any changed, it raises an error naming the table and the sorted attribute keys.
- The CLI is unchanged. `ImmutableRevisionError` isn't in `EXPECTED_FAILURES`, so it goes through the existing top-level handler: it is logged as `cli.unexpected_error` and reported in one line. That path is already tested by ticket 02's tests.

## AC-4: updating a committed row is rejected

**Tests:** `tests/service/test_immutability.py`
- `test_changing_a_committed_row_is_rejected_and_leaves_it_stored_unchanged[plugin_revision]`: changes `note`.
- `test_changing_a_committed_row_is_rejected_and_leaves_it_stored_unchanged[channel_revision]`: changes `note`.
- `test_changing_a_committed_row_is_rejected_and_leaves_it_stored_unchanged[plugin_binding]`: reassigns the JSON column `config`.
- `test_repointing_a_binding_through_its_relationship_is_rejected`
- `test_every_changed_attribute_is_named`
- `test_setting_an_attribute_to_its_current_value_is_not_a_change`
- `test_a_row_still_pending_insert_can_be_changed_before_it_is_flushed`

Each parametrized case:
1. reads the stored row on a fresh connection;
2. changes the attribute and flushes;
3. asserts `raised.value.table` and `raised.value.attributes`, and that both names appear in the message;
4. rolls back and asserts that the stored row equals the snapshot from step 1.

**Categories**
- Happy path (the guard trips): one case per guarded class.
- Failure mode: there is no failure path of its own. The guard is the failure path. Logging is n/a here: the ticket's observability section says `ImmutableRevisionError` propagates and is logged by the CLI's top-level handler, which ticket 02 tests.
- Boundaries:
  - several attributes changed at once, all named in sorted order;
  - a value set to what it already holds, which is no net change, so the flush succeeds.
- Edge cases:
  - a relationship reassignment (`binding.plugin_revision = other`). The foreign key changes only during the flush, so its column history is empty when `before_flush` runs. The first implementation checked column attributes only and missed this (red below).
  - a row still pending insert can be changed freely before its first flush.

**Known limit: in-place JSON mutation.** `PluginRevision.code` and `PluginBinding.config` use plain `JSON` without `MutableDict`. A change like `binding.config["url"] = "x"` isn't change-tracked, so it neither reaches the guard nor writes to the database. Reassigning the whole value is tracked and is rejected (the `plugin_binding` case). This is recorded as the ticket asks, and not tested.

## AC-20 review follow-up: pending relationship changes

The independent review at `ff21cdd` found that the helper checked only
`current_revision_id` before a count query autoflushed pending relationship changes.
A rejected save that assigned `channel.current_revision = None` could therefore pass
both service rejection tests, despite clearing the current pointer.

**Fix commit:** `2f23924` (`review-followups-01-06: assert revision relationship before autoflush`).
The helper now checks both the foreign key and the current Revision relationship in
`session.no_autoflush`, before any count query, then rechecks the foreign key after
the same-session count. The original pending-row and separate-connection count
assertions remain. Only test support changed; service behavior is unchanged.

**Tests:**
- `test_binding_missing_a_required_field_is_rejected_and_no_revision_is_created`
- `test_one_invalid_binding_rejects_the_whole_revision`

**Mutation reproduction:** a temporary pytest plugin outside the repository
recompiled `save_channel_revision` with this sole insertion in its rejection branch:

```python
if errors:

```

The plugin used `inspect.getsource`, replaced the first `"    if errors:\n"`
with `"    if errors:\n        channel.current_revision = None\n"`, and executed
the compiled function in `news.service.channels.__dict__` before test collection.
The real service functions and migrated SQLite database were exercised. No mocks
were added to the shipped tests, and the on-disk service source was never modified.
The plugin was enabled only with `-p pointer_mutant` and a scratch `PYTHONPATH`.
